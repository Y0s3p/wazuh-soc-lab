# Scenario 3 — Suspicious Process Execution

## Objective

Detect shell command execution through `bash -c` on a Linux endpoint using `auditd` telemetry and a custom Wazuh detection rule.

The scenario demonstrates the complete detection workflow:

```text
Process execution
      ↓
auditd
      ↓
/var/log/audit/audit.log
      ↓
Wazuh Logcollector
      ↓
Wazuh auditd decoder
      ↓
Rule 80700
      ↓
Custom rule 100200
      ↓
Wazuh alert
```

---

## Detection Hypothesis

Command execution through `bash -c` can provide useful security telemetry because it represents explicit shell command execution rather than simply starting an interactive Bash session.

The detection focuses on the combination:

```text
a0 = bash
a1 = -c
```

This makes the detection more specific than simply alerting whenever `bash` is executed.

Example:

```bash
bash -c 'whoami'
```

Expected detection:

```text
bash + -c → Alert
```

Whereas:

```bash
bash
```

should not trigger the rule.

> This scenario is intended as a detection engineering exercise. The execution of `bash -c` is not inherently malicious and should be evaluated together with additional context in a real SOC environment.

---

## Telemetry

### Data Source

**Linux auditd**

Auditd was used to monitor process execution through the `execve` system call.

The relevant audit event is:

```text
type=EXECVE
```

For example:

```text
type=EXECVE ... argc=3 a0="bash" a1="-c" a2="whoami"
```

The arguments are represented as:

```text
a0 = bash
a1 = -c
a2 = whoami
```

These fields provide the command execution context required by the Wazuh detection rule.

---

## Auditd Configuration

A temporary audit rule was initially used during testing to validate that process execution events were being generated correctly.

The final rule was made persistent in:

```text
/etc/audit/rules.d/wazuh-exec.rules
```

Configuration:

```text
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=4294967295 -k audit-wazuh-x:execute
```

The rule monitors `execve` events generated by users with an audit UID of 1000 or higher, excluding the unset audit UID value (`4294967295`).

The configuration was loaded using:

```bash
sudo augenrules --load
```

The resulting events were verified using `ausearch`.

## Detection Logic

Wazuh already provides built-in auditd decoders.

The auditd decoder extracts information from the raw audit event and exposes structured fields such as:

```text
audit.type
audit.id
audit.execve.argc
audit.execve.a0
audit.execve.a1
audit.execve.a2
```

For the test event:

```text
type=EXECVE ... argc=3 a0="bash" a1="-c" a2="whoami"
```

Wazuh decoded the event as:

```text
audit.type = EXECVE
audit.execve.argc = 3
audit.execve.a0 = bash
audit.execve.a1 = -c
audit.execve.a2 = whoami
```

### Rule 80700

The built-in Wazuh auditd rules contain rule `80700`:

```xml
<rule id="80700" level="0">
    <decoded_as>auditd</decoded_as>
    <description>Audit: Messages grouped.</description>
</rule>
```

This rule acts as a base rule for auditd events.

The custom detection rule therefore uses:

```xml
<if_sid>80700</if_sid>
```

This allows the custom rule to build on events already identified as auditd events.

The resulting detection chain is:

```text
auditd event
    ↓
auditd decoder
    ↓
Rule 80700
    ↓
Custom rule 100200
```

---

## Detection Rule

The custom rule was added to:

```text
/var/ossec/etc/rules/local_rules.xml
```

```xml
<rule id="100200" level="8">
    <if_sid>80700</if_sid>
    <field name="audit.execve.a0">bash</field>
    <field name="audit.execve.a1">-c</field>
    <description>Local: Bash executed a command using -c.</description>
    <mitre>
        <id>T1059.004</id>
    </mitre>
    <group>process_execution,command_execution,</group>
</rule>
```

### Detection conditions

The rule requires all of the following:

| Condition         | Expected value |
| ----------------- | -------------- |
| Base rule         | `80700`        |
| `audit.execve.a0` | `bash`         |
| `audit.execve.a1` | `-c`           |
| Wazuh level       | `8`            |
| MITRE ATT&CK      | `T1059.004`    |

The rule therefore detects the specific execution pattern:

```text
bash -c <command>
```

rather than every execution of Bash.

### Positive Test

The following command was executed on the monitored endpoint:

```bash
bash -c 'whoami'
```

The command generated an auditd `EXECVE` event and Wazuh generated an alert:

```text
Rule ID: 100200
Level: 8
```

The alert was confirmed in Wazuh Threat Hunting.

---

### Negative Test

A second test was performed using:

```bash
bash
```

followed by:

```bash
exit
```

No alert was generated.

This confirmed that rule `100200` does not trigger simply because Bash is executed.

The `-c` argument is required for the detection to match.

## Investigation

The alert was investigated through Wazuh Threat Hunting.

The investigation workflow was:

```text
Alert 100200
    ↓
Identify affected agent
    ↓
Review event timestamp
    ↓
Review process execution fields
    ↓
Confirm bash + -c execution
    ↓
Correlate with surrounding system activity
```

In a real SOC environment, the execution itself would not automatically be considered malicious.

Additional context should be reviewed, including:

* Executing user
* Parent process
* Process ID and parent PID
* Current working directory
* Command arguments
* TTY/session
* Surrounding authentication events
* Related file modifications
* Network activity
* Process ancestry

This additional context would help determine whether the command execution represents legitimate administration, automation, or potentially malicious activity.

## MITRE ATT&CK

The detection is mapped to:

**T1059.004 — Command and Scripting Interpreter: Unix Shell**

The technique covers execution through Unix shell interpreters such as Bash.

The mapping is included in the Wazuh rule:

```xml
<mitre>
    <id>T1059.004</id>
</mitre>
```

## Lessons Learned

This scenario demonstrated the complete path from Linux telemetry to a Wazuh detection:

```text
Behavior
  ↓
Telemetry
  ↓
Log collection
  ↓
Decoder
  ↓
Base rule
  ↓
Custom detection rule
  ↓
Alert
  ↓
Investigation
```

Key lessons:

* `auditd` can provide detailed Linux process execution telemetry.
* `EXECVE` events expose the executed program and its arguments.
* Wazuh's built-in auditd decoder can transform raw audit events into structured fields.
* Existing Wazuh decoders and rules should be investigated before creating custom components.
* Rule `80700` provides the base context for auditd events used by the custom detection.
* `wazuh-logtest` is useful for validating both decoded fields and rule matching before relying on live alerts.
* Positive and negative tests are important when validating detection logic.
* A useful detection should focus on behavior and context rather than treating every execution of a common command as malicious.

This scenario also reinforced a practical detection-engineering workflow:

> **Define the behavior → identify the telemetry → verify how Wazuh parses it → identify the relevant fields → build the detection → validate positive and negative cases → investigate the resulting alert.**
